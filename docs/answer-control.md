# Answer Control и будущая передача человеку

Отдельная граница проверяет пригодность ответа перед отправкой. Ни dense similarity, ни BM25, RRF или reranker score не являются вероятностью правильности ответа. Порог уверенности по этим scores отсутствует.

| status | Проверяемый критерий | Безопасное поведение | HTTP |
|---|---|---|---|
| answered | Утверждённый полный snapshot, нужные разделы помещаются в context, provider не abstain, все выбранные ID входят в allowlist, каждый обязательный раздел покрыт; утверждения рендерятся из полных исходных единиц и проверенного инструмента | Источники, версия и расчётные ограничения обязательны; не подтверждать реальный заказ/баланс/наличие | 200 |
| clarification_needed | Нет структурированных денежных входов, доставки, регистрации, доступности ПВЗ, права на промокод или другого необходимого пользовательского параметра | Вернуть missing_fields; не предполагать недостающие значения | 200 |
| insufficient_context | Неизвестная тема, превышение context/source budget, abstain или неполное покрытие выбранными evidence IDs | Не выдавать частичные утверждения за полный ответ; предложить уточнение/поддержку | 200 |
| requires_external_data | Требуется статус/трек реального заказа или операция возврата денег в неподключённой системе | external_data.available=false, action_performed=false; возможна справочная часть, но нет ложного статуса или выполненного действия | 200 |
| handoff_required | Явно запрошен сотрудник, требуется ручная проверка спорного случая либо разные payload одного логического раздела конфликтуют | Не выбирать удобный источник; создать только описание будущего handoff, created=false | 200 |
| system_error | Сбой retrieval/provider, повреждённый индекс, неподдержанное утверждение модели, deadline либо отклонение запроса API | Не возвращать confirmed; safe error_code, пустые sources; upstream exception text скрыт | 401/413/422/429/502/503/504 по причине |

Последнее дополнение владельца заменяет прежний трёхзначный `status`. Дополнительное поле `grounding_status` сохраняет исходную границу: confirmed только для answered, insufficient_context для предметных ограничений и error для system_error. Это не оценка вероятности, одобрение возврата или признак фактически решённой проблемы клиента.

Классификация применяется к доступным свидетельствам. Без LLM явные запросы оператора/статуса и запросы недостающих параметров могут получить безопасный ответ control-only с generation_performed=false. Типизированные calculator/catalog routes работают без LLM с generation_performed=false и usage=null. Для FAQ, которым нужна LLM selection, недоступность модели возвращает system_error503. Техническая ошибка не превращается в пустую уверенную бизнес-реплику. Синтаксическая/платёжная валидация и API access имеют отдельные safe error_code.

## Поддержка утверждений

Модель не возвращает свободный answer: ProviderDraft допускает только abstain и selections(source_id,evidence_id). ID evidence привязан к SHA-256 полного source unit. Сервер проверяет source IDs, exact text, версию, источник, preparation generation, product и цену относительно утверждённого snapshot1.1. Полные policy sections сохраняют отрицания, сроки и исключения. Произвольный парафраз, выдуманная ссылка или новый числовой факт не проходят schema/allowlist. Денежные результаты вычисляются отдельно в копейках с Decimal для скидки.

Это extractive MVP, а не универсальный semantic entailment checker: ответы длинные, свободный синтез и понимание произвольной задачи не доказаны. Проверка coverage использует консервативные доменные правила и не доказывает достаточность для любого вопроса. Наличие цитат не выдаётся за измеренное качество живой LLM. Источники о разных условиях возврата не объявляются противоречием только из-за разных рекомендаций: DR-04 и DR-05 описывают разные случаи.

Поддерживается обнаружение конфликтующих payload одного section и отклонение неутверждённого snapshot; универсальный поиск семантических противоречий между произвольными документами не реализован. Изменение business snapshot требует отдельного утверждения fingerprint и проверки versioned tools. Prompt injection в неутверждённом payload отклоняется, retrieved content отделён от system instructions, модели недоступны секреты и исполнительные tools. Один реальный injection-case проверен в block-5-live-e2e.json; универсальная устойчивость не доказана.

## Handoff contract1.0

Поля: contract_version, reason, target_queue=customer_support, idempotency_key=request_id, source_ids, required_fields, created=false, external_action_performed=false, customer_message. Будущий обработчик обязан переиспользовать idempotency_key при повторах передачи, собрать согласие/контакт/ссылку на заказ через защищённый канал, подтвердить фактическое создание обращения и только после этого выдавать идентификатор обращения. Сейчас нет ticket ID, вызова операторской системы или уведомления сотрудника. Личные контакты не собираются этим MVP и не помещаются в examples/logs.

## Учёт категорий

Защищённый GET /metrics показывает process-local counters и category_shares отправляемых API responses. Считается одна категория на HTTP-ответ /chat, включая deadline и boundary errors; поздний результат завершившегося worker не считается answered. Health/readiness и метрики исключены из знаменателя. Данные теряются при restart и не объединяются между workers. Это доли технических исходов вызовов, не доля решённых клиентских проблем. Отдельно опубликованы синтетический real-HTTP прогон с настоящей LLM и явно помеченный benchmark с provider double; их знаменатели не смешиваются.
