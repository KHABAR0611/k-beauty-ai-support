# Остаточные ограничения после corrective sprint

Статус предложения: **не реализовано, требует отдельного решения**. Runtime d897630 не менялся после независимой оценки24 вопросов. Этот набор теперь также считается известным; повторное измерение на нём не будет новой независимой проверкой.

## P1: смысловое покрытие и выбор маршрута

42/42 на известной regression не обобщились на новый набор:15/24. N21/N23 получили `answered` без выполнения полного задания по зафиксированной рубрике. В N21 цитата DR-02 действительно отрицает срочную доставку, но источник не описывает дронов; автоматический ответ не обозначает этот пробел. Это пограничная пригодность ответа, а не выдуманный тариф. В N23 правила о бонусах не заменяют запрошенный расчёт и уточнение корзины. Консервативная исходная рубрика сохранена, оба считаются false-positive status.

N01/N05/N06/N20/N22 показывают зависимость конечного intent vocabulary от формулировок: отправка, другой товар, протекание, консультант, оплата купюрами. N12/N14 показывают, что избыточные или неправильно отнесённые policy bundles по-прежнему приводят к CPU timeout.

Не рекомендуется бесконечно пополнять список фраз новыми evaluation-текстами. Следующее ограниченное изменение, если оно будет одобрено: типизированный план запроса с отдельными полями intent, requested action, object/reference, question parts, unsupported/unknown constraints и missing user fields. Рассмотреть constrained extraction той же Qwen как fallback для неизвестных правил планировщика. Каждая часть должна получить конкретное подтверждение либо явное ограничение; статус определяется отдельной проверкой плана и выбранных evidence. Это гипотеза, а не доказанная замена текущего router. Потребуются замер дополнительного CPU-вызова, отказоустойчивость и новый независимый набор. Новая тяжёлая модель, CRM, Orders API и multi-agent orchestration для этого не требуются и не добавлены.

## P1/P2: локальная производительность

Evidence-first prefix cache ускоряет повторные вопросы по общим источникам, но не устраняет cold prefill и неоптимальный контекст. Два независимых запроса превысили25s, оба безопасно вернули `system_error`. На основных прогонах host RAM достигала94%/93%; в development —96%. Один worker и меньший ctx ограничивают собственную аллокацию, но не резервируют RAM и не контролируют чужие приложения. Native inference после внешнего HTTP-timeout нельзя считать гарантированно остановленным только по коду504.

Минимальное измеренное решение для показа: заранее прогреть одну модель, один API worker, reranker off, повторно использовать проверенный индекс, завершать собственные API/модель после проверки. Этого недостаточно для обещания latency SLA. Для комфортной работы на8GB закрывать ненужные приложения вручную; их автоматическое завершение не выполнялось.

Если требуется больше запаса памяти, варианты **для отдельной проверки**:16GB RAM либо INT8-экспорт BGE-M3 с новым fingerprint/index и повторной оценкой качества. Прогнозируемый компромисс квантования — меньший вес/память и возможное изменение nearest neighbors; реальные latency/Recall для этого варианта не измерены. Переход модели не утверждён и не выполнен. Платные/cloud API не подключались.

## Решение о границе MVP

Как ограниченный технический API с точными typed tools и прозрачно показанными источниками сервис воспроизводим. Как ассистент с доказанным качеством свободных русскоязычных обращений он остаётся **PARTIAL**: целевые85% и отсутствие ложных `answered` на независимом наборе не достигнуты. Новые крупные функции не решат этот дефект. Дальнейшее изменение границы продукта или semantic planner требует отдельной приёмки; автоматически оно не начинается.
